# Mail Service API - Quick PRD

**Goal:** Build **mail-service-api**, a centralized email-sending gateway for institutional systems at DGETI. Each system authenticates via API Key and can only send emails from its authorized Microsoft 365 mailboxes. The service enforces mailbox-level authorization (each system like `control-gestion` or `sigoe` has one or more allowed `from` addresses), processes all sends asynchronously through a BullMQ/Redis queue, and supports file attachments via multipart/form-data uploads. Every send is logged in an audit table (EmailLog) with statuses PENDING → QUEUED → SENT/FAILED/RETRYING. The Microsoft Graph integration uses Client Credentials Flow with Application Permission `Mail.Send`, caches access tokens to avoid repeated token requests, and implements exponential backoff retries with `Retry-After` header respect for 429/throttling responses. Attachments are stored temporarily on disk, converted to base64, and sent as FileAttachment in the Graph API body — then cleaned up after send/failure. API Keys are stored as hashes (never plaintext), admin endpoints are protected by a separate `ADMIN_API_KEY`, and all DTOs are validated with class-validator.

**Tech Stack:** NestJS (TypeScript, strict mode), PostgreSQL 16 with Prisma ORM, Redis 7 with BullMQ for queuing, Microsoft Graph API v1.0 (Client Credentials / Application Permission Mail.Send), Multer for multipart/form-data file uploads, Swagger/OpenAPI at `/docs`, class-validator + class-transformer for input validation. Infrastructure via Podman Compose (NOT Docker) with `postgres:16` and `redis:7` images. Key environment variables: `DATABASE_URL`, `REDIS_HOST`, `REDIS_PORT`, `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, `ADMIN_API_KEY`, `UPLOAD_DIR`, `MAX_ATTACHMENT_SIZE`. Core entities: System (key, apiKeyHash), Mailbox (systemId, email, isDefault), EmailLog (status enum, provider, attempts, providerResponse, attachments metadata as JSON). No template engine — each system sends its own HTML body and subject directly.

**Scope Boundaries:** No frontend/dashboard (API only), no user authentication (system-level API Keys only), no email receiving/inbox, no template management (systems provide their own HTML), no multi-provider support (Microsoft Graph only), no webhook callbacks for delivery status, no per-system rate limiting, no permanent file storage (attachments cleaned after send), no content scanning for malware, no i18n. The critical security consideration is that `Mail.Send` Application Permission grants org-wide send capability — the API serves as the governance layer restricting each system to its authorized mailboxes only. README and all documentation must use Podman Compose commands, not Docker.
